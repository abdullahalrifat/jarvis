# Jarvis v0.6 agent platform

v0.6 extends the v0.5 local coding agent into a distributed, observable developer-agent platform while keeping local execution first-class.

## Agent teams

Define a JSON task graph and run dependency-ready tasks in parallel:

```bash
jarvis team run .jarvis/team/tasks.json --workspace . --workers 3 --accept-edits --accept-commands
jarvis team status --state .jarvis/team/board.json
```

Each writable task gets a unique Git branch and worktree outside the main checkout. The board is persisted atomically and interrupted `running` tasks are recoverable on restart.

Example task file:

```json
{
  "tasks": [
    {"id":"api","title":"API","task":"Implement the API","role":"backend"},
    {"id":"tests","title":"Tests","task":"Add integration tests","dependencies":["api"],"role":"verification"}
  ]
}
```

## Browser / Playwright agent

Install the optional browser dependency and Chromium:

```bash
pip install 'jarvis-agent-cli[browser]'
playwright install chromium
jarvis browser doctor --workspace .
```

Local agent runs receive native `browser_open`, `browser_snapshot`, `browser_click`, `browser_type`, `browser_wait`, `browser_console`, `browser_network`, and `browser_screenshot` tools.

Browser networking is deny-by-default. `about:`, `data:`, localhost and loopback addresses are allowed. To allow selected hosts:

```bash
export JARVIS_BROWSER_ALLOW_HOSTS=example.com,api.example.net
```

To explicitly allow all browser networking:

```bash
export JARVIS_BROWSER_NETWORK=allow
```

## Plugin packaging

A plugin contains `jarvis-plugin.json` plus optional `skills/`, `hooks/`, `commands/`, and `mcp/` directories. Build/install/list/remove with:

```bash
jarvis plugin build ./my-plugin ./dist/my-plugin.zip
jarvis plugin install ./dist/my-plugin.zip --approve-permissions
jarvis plugin list
jarvis plugin remove my-plugin
```

Plugin file checksums are generated at build time and verified during installation. Requested permissions require explicit installation approval.

Executable command specs live under `commands/*.json`. They run through the same Jarvis sandbox/network policy as normal commands:

```bash
jarvis plugin commands
jarvis plugin run my-plugin lint --workspace . -- --fix
```

Skills, Hooks and MCP definitions from active plugins are discovered by the normal runtime.

## Background jobs and schedules

Jarvis provides a local durable SQLite queue:

```bash
jarvis jobs submit -- local 'upgrade dependencies' --workspace .
jarvis jobs list
jarvis jobs show JOB_ID
jarvis jobs cancel JOB_ID
jarvis jobs worker
jarvis jobs daemon
```

Schedules support either bounded cron expressions or fixed intervals:

```bash
jarvis jobs schedule security-scan --cron '0 8 * * 1-5' -- local 'review dependency vulnerabilities' --workspace .
jarvis jobs schedule repo-health --interval 3600 -- local 'run repository health checks' --workspace .
jarvis jobs schedules
```

## OpenTelemetry and route calibration

All runtime paths retain JSONL traces by default. Install the optional exporter for OTLP:

```bash
pip install 'jarvis-agent-cli[telemetry]'
export OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4318
```

Benchmark runs feed empirical task success, quality, latency and incorrect-completion observations into local route calibration. Inspect a category leaderboard with:

```bash
jarvis calibrate --category code
```

Only measured benchmark/evaluation results calibrate local routing; ordinary model confidence is not used as training evidence.

## Python SDK

```python
from jarvis_cli.sdk import LocalJarvis, RemoteJarvis

local = LocalJarvis(config)
result = local.run("fix the failing unit test")

remote = RemoteJarvis("https://agent.example", "token")
run = remote.run("review this repository", workspace="/workspace/repo")
```

The SDK also supports the lease-based cloud worker protocol. An external worker can claim a queued cloud task, heartbeat while working, execute it using its own local Jarvis runtime/model configuration, and report completion to Server. Expired leases are reclaimable.

## Server execution model

There are intentionally two remote concepts:

- **Runs** are the existing reviewed Server execution path with sandboxing, evidence, streaming, approval and recovery.
- **Cloud tasks** are lease-based units for external workers. They do not bypass Run safety semantics; use reviewed Runs when Server itself should mutate a repository.

Server schedules submit into the normal Runs pipeline rather than creating a second agent engine.

## Release validation

Before promoting v0.6 to production-ready:

1. run the normal Python and packaging matrix;
2. run Postgres scheduler/cloud-lease integration tests;
3. install Chromium and execute Playwright localhost + denied-network integration tests;
4. run the seeded benchmark corpus against local Ollama and at least one remote provider;
5. verify OTLP export against a collector;
6. release `jarvis-core` v0.6 and replace development dependencies with its immutable wheel/checksum.
