# Jarvis v0.7 — Efficiency + Reliability

v0.7 optimizes the agent harness around measured evidence rather than model confidence.
It is stacked on v0.6 and keeps the existing local/remote/provider-neutral runtime.

## Runtime behavior

### Adaptive context compiler

Before a local run, Jarvis builds a bounded structural context packet from the persistent
repository graph, symbols/imports, related tests, current Git changes, and recent Git
history. Raw repository dumps are avoided. Repeated tool output within a run is
content-addressed and replaced by a digest reference.

Preview it with:

```bash
jarvis optimize context "fix AuthService login" --workspace .
```

### Semantic mutation planning and impact-aware tests

Write-enabled runs receive a structured mutation plan containing evidence-justified
files/symbols, related/importing code, tests, configuration/build files, and deployment
artifacts. A mutation to an existing path outside the plan is denied unless the agent
first explicitly inspects that path and thereby expands the evidence scope.

For nontrivial bug fixes, completion is marked incomplete when files changed but no
successful regression/verification test was recorded.

```bash
jarvis optimize policy "fix the login regression" --workspace .
```

### Speculative exploration

Ambiguous/complex read-only exploration may launch two independent explorer instances.
Each has its own provider state, token ledger, and memory artifacts. When the first
candidate reaches the evidence threshold, a cancellation signal prevents losing agents
from starting later model turns and queued work is cancelled.

Disable it with:

```bash
export JARVIS_SPECULATIVE=off
```

Token pressure can suppress speculation automatically:

```bash
export JARVIS_TOKEN_PRESSURE=0.9
```

### Dynamic escalation

Simple work starts on the normal/cheap route. If the first single-agent pass produces
failed tests, tool failures, an incomplete evidence gate, or low execution-derived
confidence, Jarvis automatically launches a bounded multi-agent repair + independent
verification pass.

```bash
export JARVIS_ESCALATE_ON_FAILURE=1
```

Remote escalation is intentionally opt-in because it can consume paid tokens:

```bash
export JARVIS_ALLOW_REMOTE_ESCALATION=1
export JARVIS_ESCALATION_PROFILE=strong-remote
```

Without this opt-in, escalation stays on configured local/current routes.

### Independent verifier

The verifier is given task/repository evidence, diff/test/workspace artifacts, and the
current state needed to verify the work. Implementer narrative/reasoning is filtered out;
the verifier is explicitly instructed to inspect the repository and evidence itself.

### Structured failure memory

Failures are persisted as bounded signatures such as rate-limit, tool protocol, syntax,
test, permission, network, wrong-symbol, and API-compatibility failures. Future tasks of
the same category receive only the highest-frequency recovery hints rather than generic
conversation memory.

```bash
jarvis optimize failures --workspace . --category bugfix
```

### Deterministic retry taxonomy

Repeated identical failures stop escalating retry cost. Guidance is failure-specific:
rate limits use fallback/backoff; malformed tools repair the provider-neutral exchange;
syntax/test failures inspect local evidence; permission/compatibility failures escalate
instead of bypassing policy.

### Evidence confidence

The final local result includes an `Efficiency/evidence` record derived from actual test
and command outcomes, independent verification, and tool failures. It is not an LLM
self-rating.

### Patch minimization

Suspiciously broad patches trigger a bounded cleanup pass that inspects the current diff
and removes unrelated formatting, debugging code, duplicate abstractions, unnecessary
dependencies, and unrelated edits. Configure the changed-file threshold with
`JARVIS_PATCH_MINIMIZE_FILES` (default 8).

### Measured task-type routing and local/remote hybrid

Calibration now queries the same task categories used by benchmark observations instead
of using the full prompt as a category key. With no trustworthy measurements, simple
tasks prefer capable local profiles; complex/risky tasks fall back to stronger configured
routing. Measured task success dominates latency/token cost.

```bash
jarvis optimize routes --category bugfix
```

### Adversarial continuous evaluation

`benchmarks/v0.7-adversarial.json` adds cases for hallucinated files/APIs, false test
success, truncated evidence, README/issue/tool prompt injection, stale/conflicting
sources, wrong-symbol edits, impact misses, patch bloat, regression proof, repeated
failures, routing escalation, verifier isolation, duplicate tool output, and context
waste.

Run it through the existing benchmark command:

```bash
jarvis bench benchmarks/v0.7-adversarial.json
```

## Safety defaults

- speculative candidates are read-only explorers;
- remote escalation is opt-in;
- mutation planning cannot broaden sandbox/network permissions;
- repository content and prior failure detail remain untrusted data;
- test success is counted from command exit evidence, not words such as “passed” in model text;
- repeated tool output deduplication is scoped to one run, so later sessions never receive a digest for content they have not seen.
