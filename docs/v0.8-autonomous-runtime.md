# Jarvis v0.8 — Autonomous Engineering Runtime

v0.8 hardens long-running local and remote engineering work around explicit ownership, evidence, permissions, cancellation and measurable execution state. The v0.8.1 post-merge audit adds release alignment, workspace trust, MCP transport/approval hardening and command-secret isolation.

## Local execution proof

Every composed local run records a durable proof ledger under `$XDG_STATE_HOME/jarvis/proofs` (normally `~/.local/state/jarvis/proofs`). The workspace path is hashed, so proof files do not dirty the repository.

```bash
jarvis proof --workspace .
jarvis dashboard --workspace . --watch
```

Proof records cover selected routes, permission decisions, approvals, tool calls, test results, failures and completion. They are execution evidence, not model chain-of-thought. Task text is represented by digest/length rather than persisted verbatim; known secret fields and bearer/provider tokens are redacted; large patch/content arguments are represented by digest and size.

## Trust and permission boundaries

Repository content is untrusted and cannot grant itself capabilities. Project `.jarvis/permissions.toml` is restrict-only: repository `allow` entries are ignored for privilege expansion, while `ask`/`deny` may make policy more restrictive.

Trusted user pre-authorization lives outside the repository at `$XDG_CONFIG_HOME/jarvis/permissions.toml` by default, or `JARVIS_PERMISSIONS_FILE`.

Read-only operations are allowed by default. Mutations ask by default. Plan mode always denies mutations. Explicit CLI `--accept-edits` / `--accept-commands` are trusted operator pre-approval, while repository policy may still deny a capability.

### Workspace trust

Executable repository configuration is a stronger boundary than permission to edit. v0.8.1 therefore does not load project-local `.jarvis/hooks.toml` until the exact resolved workspace has been trusted by the user:

```bash
jarvis trust --workspace . --status
jarvis trust --workspace .
jarvis trust --workspace . --revoke
```

Trust is stored in the user configuration directory rather than the repository. User-level Hooks remain trusted configuration. Project Skills/instructions are still treated as passive untrusted prompt context; they cannot broaden permissions.

## Secret-minimized command execution

Agent-run repository commands no longer inherit credential-like process variables by default. Provider/API keys, Server/MCP/cloud tokens, database URLs and values containing URL userinfo are removed before launching untrusted tests/build commands.

A trusted operator can opt in a required environment variable explicitly:

```bash
export JARVIS_COMMAND_ENV_ALLOW=PRIVATE_PACKAGE_TOKEN
```

This escape hatch should be used narrowly because repository code can print any allowed variable into agent/model context.

## MCP policy and transport

MCP is deny-by-default. v0.8.1 additionally enforces `requires_approval` before configured tool calls, serializes stdio startup/initialization/request state for parallel agents, avoids unread-stderr deadlocks, bounds HTTP responses, validates JSON-RPC response IDs and parses endpoints structurally. Plain HTTP is accepted only for exact loopback hosts.

See [mcp.md](mcp.md).

## Lease-fenced cloud workers

Every cloud claim receives a fresh `lease_id`. Heartbeat, state updates and completion must present the current worker ID plus lease ID. Reclaiming a task therefore invalidates a previous worker's ability to publish stale results.

```bash
jarvis cloud submit "fix the bug" \
  --repository-url https://github.com/example/repo.git \
  --git-commit <exact-commit> \
  --model auto \
  --write \
  --idempotency-key issue-123-attempt-1

jarvis cloud worker --worker-id build-host-1 --model auto
jarvis cloud status <task-id>
jarvis cloud cancel <task-id>
```

The worker runs agent execution in a killable child. Heartbeats use bounded retry/backoff. If the fence is rejected or cannot be renewed before expiry, the child is terminated and its result is not published.

Git-backed tasks use per-lease ephemeral workspaces. Worker-side repository host allowlisting remains mandatory through `JARVIS_CLOUD_GIT_ALLOW_HOSTS`.

For shared or hostile multi-tenant workloads, this host-worker model is not the final isolation target: per-task container/VM-style resource and egress isolation remains a P0 production gap.

## Model routing and credentials

`model=auto` keeps calibrated worker configuration. A named profile switches provider, model, endpoint, output limits and its own API-key source. Raw model identifiers stay on the worker's existing provider/endpoint. Provider credentials are never sent in cloud task payloads, and a profile changing provider/endpoint cannot inherit another provider's API key.

## Background jobs and schedules

Local job cancellation terminates the complete spawned process tree rather than only the direct child. POSIX workers use process groups; Windows uses `taskkill /T`.

Cron schedules use conventional five-field semantics including lists/ranges/steps, Sunday as `0` or `7`, DOM/DOW OR behavior when both are restricted, UTC evaluation and bounded next-occurrence search.

These CLI jobs are not yet equivalent to a first-class nonblocking **agent tool** for starting a dev server or long test while the reasoning loop continues; that remains a developer-parity gap.

## Release alignment

The v0.8.1 consumer line pins the verified immutable Core v0.8.0 release wheel:

```text
SHA-256 d9569b69385e58a681ea01e900eb81c395d3f202a09a92878eb82bf4d4b8618a
```

Public Python SDK cloud types now resolve to the fenced/idempotent implementations. The release tag check reads the literal package version without importing runtime dependencies before installation.

## Release gates and current status

Expected release gates:

1. Core Black/Ruff/pytest/coverage/build/Twine and immutable artifact verification.
2. Jarvis Python 3.10/3.12/3.13, Black/Ruff, full pytest/coverage, package build and clean-wheel install.
3. AI Stack Server unit tests, dedicated Postgres fencing/idempotency integration, UI/Compose, supply-chain and model integration.
4. Cross-repository Core + CLI + Server/Postgres smoke validation using exact release candidates.
5. Security regression tests for workspace trust, MCP approval/transport and command secret isolation.

Core v0.8.0's public artifact has been verified. Private Jarvis/AI Stack Actions currently fail before runner provisioning (`steps:null`), so v0.8.1 is **not release-certified** until those executable gates run.

For the remaining production and Claude/Codex-class gaps, see [world-class-readiness.md](world-class-readiness.md).
